## 一、为什么要改造——说清楚「原来的问题」

这是面试最重要的部分。**能讲出「为什么改」比「改成什么样」值钱得多。**

原版：

```c
while (1) {
    qmi8658_fetch_angleFromAcc(&value);   // 读 I2C + 算角度
    lv_label_set_text(a, buf);            // 刷屏
    vTaskDelay(pdMS_TO_TICKS(10));
}
```

三个动作**串行**执行，总耗时 = 读传感器 + 算角度 + 刷屏幕。
其中 LVGL 刷屏是最慢的一环（一次几毫秒到几十毫秒）。

后果：**传感器采样被屏幕刷新拖累，实际采样率远低于预期的 100Hz**。
快速转动传感器时，采到的点稀疏，画出来的角度曲线是**台阶状**而不是平滑的。

一句话总结（面试就这么说）：
> 单任务架构下，慢环节（UI）会阻塞快环节（采集），
> 导致传感器采样率不达标。改多任务是为了**让采集不受 UI 影响**。

## 二、代码走读

### 1）为什么优先级是 3 / 2 / 1

```c
xTaskCreate(task_sample,  "sample",  4096, NULL, 3, NULL);
xTaskCreate(task_process, "process", 4096, NULL, 2, NULL);
xTaskCreate(task_ui,      "ui",      4096, NULL, 1, NULL);
```

FreeRTOS 是**抢占式调度**：高优先级任务就绪时立即抢占低优先级任务。

- **采集最高**：传感器数据有时效性。晚 10ms 读，那个时刻的姿态就永远采不到了。
- **UI 最低**：屏幕慢一点人眼看不出来（20Hz 已经流畅），但不能拖慢采集。

**追问：「如果 UI 优先级最高会怎样？」**
> 屏幕一刷新就抢占采集任务，采样点大量丢失，姿态数据失真。
> 实时系统里优先级分配的原则是：**越靠近数据源、时效性要求越高的任务，优先级越高**。

### 2）为什么采集任务用阻塞时间 0

```c
if (xQueueSend(q_raw, &raw, 0) != pdTRUE) {
    ESP_LOGW(TAG, "raw queue full, frame dropped");
}
```

第三个参数是**最大阻塞时间**，给 0 表示「队列满了立刻返回，绝不等待」。

这是整个架构里最关键的一行。反过来想：如果这里写 `portMAX_DELAY`，
当解算任务卡住时，采集任务会一直阻塞等待队列空位——
**I2C 时序因此被打断，传感器采样彻底停摆**。

设计原则：**采集端宁可丢数据，也不能停**。
丢一帧只是少一个采样点；停下来就是整段数据失效。
这也是为什么日志打的是 `ESP_LOGW`（警告）而不是 `ESP_LOGE`（错误）——丢帧是可接受的正常降级。

### 3）为什么解算任务用 portMAX_DELAY

```c
if (xQueueReceive(q_raw, &raw, portMAX_DELAY) == pdTRUE) { ... }
```

这里反过来：**没数据就一直挂起**。

队列相比「全局变量 + 轮询」的核心优势就在这：
任务在 `xQueueReceive` 上阻塞时，CPU 会调度给其他任务，不空转。
如果用轮询（`while(!flag) vTaskDelay(1)`），既浪费 CPU 又有延迟。

一句话：**生产者不能等，消费者可以等**。

### 4）队列长度为什么只要 5 和 3

```c
q_raw      = xQueueCreate(5, sizeof(raw_data_t));
q_attitude = xQueueCreate(3, sizeof(attitude_t));
```

**这是面试高频陷阱题。** 很多人觉得队列越长越安全，其实相反：

队列的作用是**缓冲瞬时抖动**（比如某次刷屏特别慢），不是存储历史数据。
如果队列长度 100，UI 慢的时候会积压 100 帧，
等 UI 终于有空了，它刷出来的全是**几百毫秒前的旧角度**——延迟感非常明显。

所以：队列长度 = 能吸收瞬时抖动就够了，通常 **3~10**。
实时系统的口号是：**宁可丢旧数据，不要送旧数据**。

### 5）栈为什么给 4096

```c
xTaskCreate(task_ui, "ui", 4096, NULL, 1, NULL);
```

单位是 **word**。ESP32 是 32 位，1 word = 4 字节，所以 4096 ≈ **16KB**。

给少了会栈溢出，设备随机重启（而且很难排查）。
UI 任务因为要调 LVGL（调用栈深），必须给足。
调试手段：用 `uxTaskGetStackHighWaterMark()` 看实际用了多少，再往回收。

### 6）解算函数为什么抽出来

```c
static void attitude_from_acc(const raw_data_t *raw, attitude_t *att)
{
    temp = (float)raw->acc_x /
           sqrtf((float)raw->acc_y * raw->acc_y + (float)raw->acc_z * raw->acc_z);
    att->roll = atanf(temp) * RAD_TO_DEG;
    ...
}
```

原版 `qmi8658_fetch_angleFromAcc()` 把「读寄存器」和「算角度」耦合在一个函数里，
所以没法拆任务——你不能在解算任务里调用它，因为它会自己去读传感器。

抽出来之后，这个函数变成**纯函数**（输入原始值，输出角度，不碰硬件），
好处是：
- 可以单独测试（喂一组已知加速度值，检查角度对不对）
- 解算任务因此不需要访问 I2C，职责真正单一

**公式与原版完全一致**，改造只改结构，不改算法——这是重构的正确做法。

## 三、面试问答（必须能答）

**Q：为什么要用多任务？单任务不行吗？**
> 功能上能跑，但采样率不达标。单任务下 LVGL 刷屏会阻塞传感器读取，
> 实测（原版）快速转动时角度曲线呈台阶状。
> 多任务让采集不受 UI 影响，采样率稳定在 100Hz。

**Q：任务之间为什么用队列，不用全局变量？**
> 三个原因：
> ① **线程安全**：全局变量的读-改-写不是原子操作，两个任务同时访问会出错，队列内部有临界区保护；
> ② **阻塞机制**：消费者可以在队列上挂起，没数据时不占 CPU，全局变量只能轮询；
> ③ **解耦**：生产者和消费者不需要知道对方的存在，改一边不影响另一边。

**Q：队列满了怎么办？**
> 采集端丢弃当前帧（阻塞时间 0），并记录一条 WARNING 日志。
> 设计原则是采集不能停——丢一帧只是少一个采样点，停了就是整段数据失效。

**Q：如果两个任务同时写一个全局变量会怎样？**
> 数据竞争。比如 `count++` 实际上是「读-加-写」三步，
> 两个任务交叉执行会得到错误结果。
> 解决方式：用队列传递（推荐）、用互斥量 `xSemaphoreCreateMutex()` 保护、
> 或者关中断进入临界区（只适合极短操作）。

**Q：优先级反转是什么？怎么避免？**
> 低优先级任务持有锁，高优先级任务等锁，中等优先级任务抢占 CPU——
> 导致高优先级反而最后执行。
> 避免：用优先级继承的互斥量（`xSemaphoreCreateMutex()` 在 FreeRTOS 里带优先级继承），
> 或者设计时减少共享资源，用队列代替锁。

**Q：怎么知道栈给够了没有？**
> 用 `uxTaskGetStackHighWaterMark(NULL)` 查「栈历史最小剩余量」。
> 如果还剩很多就调小，接近 0 就调大。我这个项目给 4096 word（约 16KB）是保守值。

**Q：这个方案还有什么不足？**
> ① 纯加速度解算在动态场景下会抖（加速度计对运动敏感），
>    应该用**互补滤波或卡尔曼滤波**融合陀螺仪数据；
> ② 采集是固定 10ms 轮询，理想做法是用 QMI8658 的数据就绪中断（INT 引脚）
>    触发二值信号量，避免空读；
> ③ UI 队列用 `xQueueSend` 会积压，改用 `xQueueOverwrite()` 只保留最新一帧更合适。

## 四、动手改（挑一个做，面试立刻有话说）

1. **加互补滤波**：`angle = 0.98 * (angle + gyro * dt) + 0.02 * acc_angle`，解决动态抖动
2. **改用中断驱动**：QMI8658 数据就绪引脚 → 二值信号量 → 采集任务
3. **`xQueueOverwrite()`**：UI 队列永远只保留最新一帧
4. **加栈水位监控**：每 10 秒打印一次三个任务的栈剩余量，验证 4096 够不够
